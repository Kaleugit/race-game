# AGENTS.md - Core Multi-AI Workflow

This file defines the base workflow for development with AI agents in this repository.

## Objective
Standardize execution across providers (Claude, Codex, and others), while keeping one contract for quality, memory, and delivery.

## Golden Rules
1. KISS: prefer simple solutions.
2. YAGNI: do not implement what was not requested.
3. DRY: eliminate duplication.
4. RTFM: read the official docs/source for any system, lib, tool, or API before assuming behavior. No guessing how things work.
5. No code without planning.
6. Fix root cause; never mask symptoms.
7. Never change tests just to "make them pass".
8. Document decisions and outcomes.

## CI/CD Change Authorization (Blocking — ADR-016)
Any action that directly affects this project's CI/CD requires prior, explicit
authorization from the project manager (gestor do projeto). Minimum scope:
`.governance/ci-mode.conf`, `.github/workflows/**`, `scripts/validate-*`,
`scripts/reconcile-*.sh`, `scripts/run-tests.sh`,
`.governance/validate-baseline.txt`, branch-protection/required-checks
configuration, and delivery auto-merge behavior.

Before performing such an action without a recorded authorization, the agent
MUST display the following warning verbatim (PT-BR, user-facing literal) and
STOP — do not proceed, do not work around it:

> "Essa ação interfere diretamente no CI-CD desse projeto e deve ser autorizada
> pelo gestor do projeto, caso não tenha a autorização agora, pare por aqui e
> volte quando tiver."

An authorization is "recorded" when the manager stated it explicitly for the
specific action in the current conversation, or it is written in the task
artifact / `docs/decisions.md`. Authorization for one action does not extend to
the next. Rationale and incident history: `docs/decisions.md` ADR-016.

  - Claude: `CLAUDE.md`

## Language Policy
- AI-facing operational artifacts must be written in English.
- Human/product-facing documentation must use the project language.
- Do not mix languages inside the same file.
- All text files must use UTF-8 encoding.
- Reference: `docs/language-policy.md`.

## Source Code Convention (`src/`)
- Application source code must live in `src/`.
- In monorepo/multi-service setups, each app/package must use its own `src/` (for example: `apps/api/src`, `packages/core/src`).
- Outside `src/`, keep only non-source artifacts (docs, memory, skills, configs, scripts, and high-level tests).
- Exceptions must be approved by a human and recorded in `docs/decisions.md`.

## Governance Runtime Artifacts
- The `.governance/` directory holds AI-only runtime artifacts regenerated by `skills/gen-governance-core` from the canonical source documents.
- Files: `.governance/CORE.md` (L2), `.governance/MINI.md` (L1), `.governance/SUBAGENT.md` (L3), `.governance/meta.yaml` (audit metadata).
- On Claude Code, the runtime auto-injects the appropriate level via hooks:
  - `SessionStart` and `PostCompact` → `CORE.md` (L2)
  - `SubagentStart` → `SUBAGENT.md` (L3)
  - `UserPromptSubmit` → `MINI.md` (L1) every turn
- **Do not** call `Read()` on any file under `.governance/` when running under Claude Code — the content is already in context. Re-reading wastes tokens and dilutes attention.
- On providers without hook support (e.g., Codex direct), read `.governance/CORE.md` once at task start as part of mandatory reading.
- Humans never read these files. To change behavior, edit the source documents (`AGENTS.md`, `INTEGRITY-RULES.md`, `CLAUDE.md`, `docs/PROJECT_SPECS.md`, etc.) and run `/gen-governance-core`.

## Mandatory Reading At Task Start
### Base (all modes)
1. `docs/PROJECT_SPECS.md`
2. `memory-system/1-project-context.md`
3. `memory-system/2-tasks.md`
4. Latest entries in `memory-system/session-log.md` and latest fragments in `memory-system/session-log.d/*.md` (if present)
5. `memory-system/workstreams/[workstream]/notes.md` and latest fragments in `memory-system/workstreams/[workstream]/notes.d/*.md` for task-relevant workstreams (if present)
6. `.governance/CORE.md` — **only on providers without Claude Code hooks**; otherwise the runtime already injected it.

### Additional by mode
- `Quick`: base only + existing artifacts for the same task (if any).
- `Standard`: base + `memory-system/task-docs/TASK-<github-login>-<task-key>-[role|workstream]-planning-[YYYY-MM-DD].md` (or create it).
- `Critical`: base + task planning/report and impacted architecture/contract docs.

### Task-relevant extended specs
- When a task touches a domain covered by `docs/specs/*.md`, the agent must also read the relevant spec(s).
- `docs/specs/` is optional. Projects with a single `docs/PROJECT_SPECS.md` do not need it.

## Project States (Bootstrap)
- `PRE_BOOTSTRAP`: `BRIEFING.md` is still template/placeholder (no project-specific briefing yet).
- `INCOMPLETE`: first project-specific `BRIEFING.md` exists and bootstrap artifacts are being iterated.
- `COMPLETE`: bootstrap artifacts are human-approved and ready for epic/task planning.
- `READY_FOR_EXECUTION`: epic planning is approved; normal task orchestration is enabled.

Mandatory file in `PRE_BOOTSTRAP` state:
- `BRIEFING.md` at repository root, with free-form project description.

## Gate 0: Bootstrap (Advisory)
Incomplete bootstrap is an accepted risk at project start.
Gate 0 exists to signal risk and guide human/architect decisions, not to syntactically block work.

### Rule
- Prefer finishing bootstrap and planning before starting regular implementation tasks.
- `PRE_BOOTSTRAP`, `INCOMPLETE`, and `COMPLETE` are bootstrap/planning stages (main-friendly, advisory validation).
- Normal implementation orchestration should start at `READY_FOR_EXECUTION`.
- Bootstrap/planning remains a special case and may happen directly on `main`, with intermediate commits and warning-level validation.

### Criteria by state
- `PRE_BOOTSTRAP`:
  - `BRIEFING.md` is still placeholder/template.
- `INCOMPLETE`:
  - `BRIEFING.md` has at least a first real project-specific version.
  - `docs/PROJECT_SPECS.md` and `memory-system/1-project-context.md` may still be drafts.
  - Pending items/ambiguities still require human confirmation.
- `COMPLETE`:
  - All minimum bootstrap criteria below are validated.
  - Human explicitly approves that `PROJECT_SPECS` is ready to be decomposed into epics.
- `READY_FOR_EXECUTION`:
  - `docs/EPICOS.md` is approved by human.
  - Bootstrap gate in `memory-system/2-tasks.md` is updated by `gen-epics`.

### Minimum criteria to consider bootstrap complete
`docs/PROJECT_SPECS.md`:
- Product name, main objective, problem statement, and target audience are filled.
- At least one item in the included scope section.
- At least one functional requirement (`RF-XXX`) is filled.
- At least one acceptance criterion (`CA-XXX`) is filled.
- `Last updated` has a real date (not `YYYY-MM-DD`).
- Section 10 (Decision Criteria) has at least the default criteria present.

`memory-system/1-project-context.md`:
- `Name`, `Type`, `Status`, and `Last Updated` are filled with real values.
- At least one goal in `Project Goals`.
- At least one area in `Active Development Areas`.

`docs/PREREQUISITES.md`:
- File exists and has been reviewed (categories evaluated).
- Blocking items for automated execution are either resolved or explicitly pending with owner.

`docs/specs/` (when present):
- Each spec file is self-contained (an agent can understand the domain by reading it + `PROJECT_SPECS.md`).
- No contradictions with `docs/PROJECT_SPECS.md` or `BRIEFING.md`.

### When bootstrap is not ready for execution
- Record the block in the task file under `memory-system/tasks/` using `Blocked By: Bootstrap incomplete`.
- Prioritize bootstrap/planning tasks as highest priority.
- If there is doubt in mapping from `BRIEFING.md`, ask the human before closing bootstrap.
- Syntax CI should emit `WARN` for incomplete bootstrap, without blocking on bootstrap placeholders.

## Skill Taxonomy (Persona vs Workflow)
- Authoritative reference: `skills/gen-skill/references/interoperable-skills-model.md`.
- Every skill (`skills/<skill>/SKILL.md`) must declare `metadata.kind: persona | workflow` in frontmatter.
- `persona` skills are judgment-oriented (analysis, review, design, trade-offs).
- `workflow` skills are execution-oriented (repeatable steps, operational evidence, delivery flow).
- Do not create hybrid skills. If both behaviors are needed, split into two skills and orchestrate them.
- `workflow` skills may delegate judgment to `persona` skills during execution (orchestration pattern).
  The workflow defines when/why to delegate; the persona provides expertise.
  Provider dispatches the delegation: Claude Code via subagent adapters, Codex via inline context.
- Provider discovery via symlinks:
  - `.claude/skills -> ../skills` (Claude Code)
  - `.agents/skills -> ../skills` (Codex)
- Provider adapters:
  - `persona` skills require a thin Claude subagent adapter in `.claude/agents/<skill>.md` with `skills: [<skill>]` preloading.
  - `workflow` skills need NO adapter. The `.claude/skills` symlink makes them available as `/<skill>` commands automatically.
  - `.claude/commands/` is deprecated and must not contain files.
  - Codex uses `skills/<skill>/SKILL.md` directly as the behavioral source of truth.
- Claude adapter files must use valid YAML frontmatter expected by Claude Code.
  - Minimum for persona adapter: `name`, `description`, `model: inherit`, and `skills` preloading the canonical skill.
- CI syntax checks must validate metadata and adapter consistency.

## Subagent Delegation Model
Workflow skills that orchestrate other skills via subagents (Agent tool) must follow these rules:
- Each subagent gets isolated context. Do not assume shared state between subagents.
- The orchestrator is responsible for passing context between subagents explicitly (e.g., inter-task context, contract warnings).
- Subagents must return structured results that the orchestrator can parse. Define the return protocol in the skill's references.
- On subagent failure (timeout, crash, malformed return): retry once with error context, then mark the unit of work as blocked.
- Subagents may delegate to persona skills (creating depth-3 delegation: orchestrator -> subagent -> persona). This is allowed and expected for Standard/Critical mode.
- Resource budgets: orchestrators should manage accumulated context size (summarize when exceeding ~2000 tokens).
- Anti-contamination: subagents performing analysis must not read prior analysis results to avoid anchoring bias.
- Read-only agents on a SHARED working tree must not mutate it: when an orchestrator fans out concurrent read-only subagents (e.g. `review`/`review-spec`/`ep-check` dimensional agents) over its OWN checkout, those agents MUST NOT run `git stash`/`checkout`/`reset`/`restore` or any command that changes the working tree — doing so corrupts the tree the orchestrator and sibling agents are reading (e.g. ep-check's working-tree-vs-baseline diff starts lying). To inspect another ref, use `git show <ref>:<path>` (pure read, never touches the tree). This restriction applies ONLY to agents sharing the orchestrator's working tree; an agent in its OWN isolated worktree may mutate its own tree freely (checkout/commit as needed).
- Skills using this model: `gohorse` (default epic executor — Workflow tool fanning out per-task worktree-isolated subagents; parallel implement + serial delivery + claim-on-first-touch file ownership), `gohorse-light` (sequential per-task subagents; dependency-free stable fallback for `gohorse`), `review-spec` (per-dimension subagents), `review-all` (per-doc subagents), `parallel` (per-task tmux workers).
- Isolation verification (mandatory before first write): every subagent that writes/commits MUST verify its worktree isolation before the first write — confirm `git rev-parse --show-toplevel` is NOT the primary repo root and `git rev-parse --abbrev-ref HEAD` is its own task branch (use `./scripts/assert_isolated.sh --expected-branch <branch> [--require-clean]`). If isolation cannot be confirmed, ABORT and report — never infer a worktree from the list of existing worktrees.
- Orchestrator anti-pattern: do NOT combine `team_name` with `isolation: worktree` — isolation is silently dropped (anthropics/claude-code #33045) and worktrees can be silently reused stale (#51596). Either use `isolation: worktree` WITHOUT `team_name`, or provision `git worktree add` explicitly per agent and pass the path. Never assert "you are isolated" as a premise — instruct the agent to VERIFY. On a non-isolation report, ABORT that unit of work; never reply "go ahead and commit".
- Manual launches (human operators): when launching agent teams or ad-hoc agents OUTSIDE the boilerplate skills, the same rules apply — provision an explicit isolated worktree per agent, never pair `team_name` with `isolation: worktree`, and run `./scripts/install-pre-commit-hook.sh` so the isolation guard blocks task-branch commits made from the primary repo regardless of how the agent was spawned. See `boilerplate-docs/manual-agent-launch-safety.md`.

## Execution Modes
### Decision precedence
1. Explicit human decision.
2. Automatic risk classification by the agent.

If there is no explicit human decision and no clear trigger, default mode is `Standard`.
`Quick` is optional and should be chosen explicitly by human+architect for low-risk fast paths.

### Entry criteria
- `Quick`: low risk, no contract/schema/infra change, up to 3 changed files, and estimated effort up to 2h.
- `Standard`: default mode for regular execution when no other mode is explicitly selected.
- `Critical`: security changes, data migration, breaking contract/interface change, sensitive deploy, or high regression risk.

### Obligations by mode
| Dimension | Quick | Standard | Critical |
|------|------|------|------|
| Planning | Minimal planning recorded in task item | Unified planning doc using template | Unified planning doc using template with full risk coverage |
| Artifacts | Full planning/report not required | planning + report | planning + report |
| Human approval | Not required by default | Required when ambiguity or high risk exists | Required at Architecture, Testing, and Integration gates |
| Minimum testing | Verifiable `unit` or `manual` | Risk-based selection (`unit`/`integration`/`e2e`/`manual`) | `unit` + `integration` required; `e2e` when applicable |
| Evidence to close | Objective `PASS`/`FAIL` result with executed command/check | Traceability `Requirement -> Criterion -> Test` + evidence | Full traceability + explicit evidence per criterion |
| Memory/docs updates | Update task file and fragments (`session-log.d`/`notes.d`) | Full standard flow | Full standard flow + explicit updates to impacted docs |

### Mode escalation
- Any role may escalate `Quick -> Standard/Critical` when new risk is discovered.
- Downgrade is allowed only with explicit justification in the task artifact.
- If expected behavior, scope, or `PASS/FAIL` are ambiguous, pause and escalate to human.

### Governance by mode (syntactic and semantic)
- Syntax CI should apply minimum rigor by mode:
  - `Quick`: required task fields and objective `Evidence` (`PASS/FAIL` + command/check) when closing.
  - `Standard`: `planning` required; `report` required when closing.
  - `Critical`: `planning + report` required.
- CI must remain syntactic/structural (fast and simple), without validating business semantics.
- Semantic validation (skill `delivery`) checks completeness, consistency, and content coherence.
- Project decision: placeholders in `Planning`/`Report` references cannot pass syntax gate for `Standard/Critical` tasks.
- Operational rule: Gate 0 bootstrap is advisory and depends on human/architectural risk validation.

## Standard Workflow
1. Check Gate 0 bootstrap and record risk when status is not `READY_FOR_EXECUTION`.
2. Select highest-priority task from `memory-system/2-tasks.md` and open the file under `memory-system/tasks/`.
3. Define execution mode (`Quick`, `Standard`, `Critical`) using precedence rule (`Standard` by default).
4. Define relevant task workstreams (reuse existing or create new).
5. Create/use task worktree/branch before coding.
6. Mark task as `IN_PROGRESS`, update `Last Updated`, and record chosen mode.
7. Define test strategy and verifiable acceptance criteria before coding (use `skills/testing/` when applicable).
8. Produce artifacts required by selected mode.
9. Implement the change with minimum necessary scope.
10. Run legitimate tests required by selected mode.
11. Record `PASS`/`FAIL` evidence according to mode requirements.
12. Implementation skills must commit only on the task branch; PR open/update is exclusive to `skills/delivery/`.
    `skills/implement` must finish with a delivery handoff and must not invoke `skills/delivery/` directly.
    When requested by human (or a supervisor workflow), run `skills/delivery/`: validate semantic contract and, if adherent, open/update PR from task branch to `main` with merge after CI.
   Exceptions: bootstrap and documentation-only tasks may be delivered directly to `main` when exception guardrails are satisfied.
13. If structural organization is needed, suggest/trigger `skills/housekeeping/`.
14. `skills/delivery/` closes delivery ownership in the task file (`Status`, `Completed`, `Last Updated`, delivery metadata).
15. Update session logs in `memory-system/session-log.d/*.md`, update other mode-required docs, and keep task consistent in `memory-system/tasks/*.md`.
   - Record sessions in `memory-system/session-log.d/*.md` fragments (append-only); `session-log.md` is consolidated on `main`.
   - Record workstream notes in `memory-system/workstreams/*/notes.d/*.md`; `notes.md` is consolidated on `main`.
   - Boilerplate-local exception: for documentation-only and governance tasks executed directly in this boilerplate repository (e.g., bootstrap iterations, doc updates, skill authoring), do not create `memory-system/tasks/*`, `memory-system/task-docs/*`, or `memory-system/session-log.d/*`; keep objective evidence in the execution output and validation commands. Implementation tasks that change scripts, CI, or skill logic must use the normal task flow even within the boilerplate.

## Documentation Main Flow (Exception)
- Documentation-only tasks may be committed/pushed directly on `main`.
- Direct `main` delivery for documentation must keep changes in documentation scope only:
  - any Markdown file (`**/*.md`) to support new documentation locations without CI allowlist updates
  - `docs/**`
  - `memory-system/**`
  - `boilerplate-docs/**`
  - `.claude/agents/**`
  - `skills/*/references/**`
- If any changed file is outside this scope, use normal delivery flow (task branch + PR + CI).
- Preferred command for this exception: `./skills/delivery/scripts/deliver-to-main.sh --docs-main`.
- CI/docs-only delivery checks must reuse `scripts/validate-docs-only-scope.sh` as the source of truth.

## PR Delivery: Draft-First (ADR-018)
- Every PR opened by `deliver-to-main.sh` is created as a **draft** and is marked ready
  (`gh pr ready`) only as the final step of the delivery, after the last push to the branch.
- Rationale: while a PR is in draft the `Governance Validation` job is skipped by a job-level
  condition, which allocates no runner and bills **zero minutes**. A runtime early-exit does not
  save anything — the runner still starts and GitHub bills a full minute per job.
- Because `synchronize` remains among the workflow's trigger types, **any push after the PR is
  marked ready re-validates automatically**. There is no manual re-cycle to remember, and the
  check can never remain attached to a stale commit.
- Never mark a PR ready by hand before the local gate passes: marking ready is what triggers the
  validation run, and a red check is the only signal the manager has (this repository has no
  required checks).
- If `gh pr ready` fails, the delivery aborts on purpose. A PR left in draft cannot be merged and
  will not be validated — recover with `gh pr ready <n>` rather than merging around it.
- **Auto-merge is opt-in** (`--auto-merge`). It is off by default because GitHub refuses to enable
  auto-merge on a draft PR, and without required checks it merges immediately, before validation
  finishes (incident: PR #266).

## Specification Governance
- Every project based on this boilerplate must maintain `docs/PROJECT_SPECS.md`.
- `docs/PROJECT_SPECS.md` is the source of truth for scope, requirements, and acceptance criteria.
- The architect owns maintenance of this document.
- Relevant architectural or functional change must be reflected in this file before execution.
- Complex projects may split specifications into multiple files under `docs/specs/`:
  - Each file must be self-contained: an agent can understand the domain by reading it plus `docs/PROJECT_SPECS.md`.
  - File naming: descriptive, kebab-case (e.g., `docs/specs/api-contracts.md`, `docs/specs/data-model.md`).
  - Cross-spec references use relative markdown links.
  - `docs/PROJECT_SPECS.md` remains the root spec; `docs/specs/` files are domain extensions.
  - Consistency across specs is validated by `/review-spec` and `/review-all`.
- `docs/PREREQUISITES.md` tracks items the human must resolve before automated execution.
  - Generated by `/bootstrap`, validated by `/review-spec` (V6 dimension).
  - Blocking prerequisites must be resolved before `/gohorse` or `/xgh`.

## Task State Model
- Allowed states: `PENDING`, `IN_PROGRESS`, `BLOCKED`, `COMPLETED`, `CANCELED`.
- Allowed transitions:
  - `PENDING -> IN_PROGRESS | CANCELED`
  - `IN_PROGRESS -> BLOCKED | COMPLETED | CANCELED`
  - `BLOCKED -> IN_PROGRESS | CANCELED`
- Do not use states outside this flow.

## Collaboration And WIP
- Default: parallel execution is allowed with no WIP limit.
- Each task must have its own branch (`TASK-<github-login>-<task-key>-[role|workstream]`), except bootstrap when agreed.
  - Consolidating several tasks into one branch/PR violates this rule. Bootstrap is the ONLY sanctioned exception; there is no "consolidated PR" exception.
  - When the flow starts heading there — a request to "keep going on the same branch/PR" for a task that is not the one owning that branch, a `Branch:` field naming a branch that belongs to another task, or resuming work on a branch already declared by a different task file — the agent MUST WARN the human, name this rule, and stop. Never proceed silently, and never relax the rule to make a validator green.
  - `Branch:` records the branch that ACTUALLY exists. Never copy `Suggested Branch:` from an epic's `TASKS.md` into it as if it were fact — a suggestion is an intention, and INC-2026-08-17 (see `docs/decisions.md` ADR-015) shipped 23 task files pointing at branches that were never created because nothing verified it.
  - Enforced by `./scripts/assert_isolated.sh` (both modes) and, in bulk, by `./scripts/validate-conventions.sh`.
- Each agent must use its own `git worktree`.
- Memory conflicts should be mitigated by append-only logs and isolated task files in `memory-system/tasks/`.
- `memory-system/2-tasks.md` is consolidated; task branches must not edit the index manually.
- `memory-system/session-log.md` and `memory-system/workstreams/*/notes.md` are consolidated; branches must edit only `*.d/*.md` fragments.
- CI on `main` automatically reconciles consolidated artifacts (`2-tasks.md`, `session-log.md`, `workstreams/*/notes.md`).
- Merge to `main` must happen via `skills/delivery/` with passing CI validation.
  - Exceptions: bootstrap and documentation-only direct `main` flow when exception guardrails are satisfied.
- Operational guide: `docs/worktree-collaboration.md`.

## Testing Strategy (Pragmatic Test-First)
- Define what to test before implementation.
- Select testing levels by risk (`unit`, `integration`, `e2e`, `manual`).
- Map requirement -> acceptance criterion -> test.
- Bug fixes must include a verifiable reproduction scenario.
- Governance CI only validates syntactic test evidence presence; result quality is semantic (agent + human).

## Test Escalation Rule
- If the agent does not have clarity about what to test or what defines `PASS`/`FAIL`, ask the human before implementing or closing the task.

## Task Board Requirements
Each task in `memory-system/tasks/TASK-<github-login>-<task-key>.md` must include at minimum:
- `Status` (`PENDING | IN_PROGRESS | BLOCKED | COMPLETED | CANCELED`).
- `Priority` (1-5, 1 = highest).
- `Depends On` (list of `TASK-<github-login>-<task-key>` or `None`).
- `Blocked By` (current blocker or `None`).
- `Branch` (`TASK-<github-login>-<task-key>-[role|workstream]`).
- `Workstreams` (list or `None`).
- `Execution Mode` (`Quick | Standard | Critical`).
- `Last Updated` (`YYYY-MM-DD HH:MM`).
- Consolidated index is generated only in `main` CI (`memory-system/2-tasks.md`).
- Additional fields by mode/state:
  - `Standard/Critical` in `IN_PROGRESS|BLOCKED|COMPLETED`: `Planning`
  - `Standard/Critical` in `COMPLETED`: `Report`
  - `Quick` in `COMPLETED`: `Evidence` (`PASS/FAIL` + command/check)
  - Delivery tracking (optional, no new state): `Delivery Handoff`, `Delivery PR`, `Delivery Status`, `Delivery Merged At`

## Task And Git Conventions
- Task ID: `TASK-<github-login>-<task-key>`
- Task key:
  - epic-linked task: `EP-<nnn>-<tt>` (epic ID + task number)
  - ad-hoc task: generated timestamp key `YYYYMMDDHHMMSS`
- Branch: `TASK-<github-login>-<task-key>-[role|workstream]`
- Commit: `<type>(task-<github-login>-<task-key>[-<scope>]): <description>`
- Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`
- Issue references in commits:
  - Use `Closes #N` / `Fixes #N` only when the commit resolves the entire issue. GitHub auto-closes the issue on merge to the default branch, so a partial fix would close it prematurely.
  - For multi-Problem issues (issues that enumerate several sub-problems), use `Addresses issue #N Problem X` and explicitly state which Problems remain open. Keep auto-close keywords off until the final PR that resolves the last Problem.
  - When in doubt, prefer the non-closing reference and close the issue manually after verifying all Problems are resolved.
- Generate IDs:
  - ad-hoc: `./scripts/generate-task-id.sh --login <github-login>`
  - epic-linked: `./scripts/generate-task-id.sh --login <github-login> --epic-id EP-001 --task-number 01`

## Changelog Governance
- `CHANGELOG.md` is an incremental list of changes.
- Append new entries to the active unreleased/release section; do not rewrite old entries as if the file were a narrative report.
- Corrections to historical changelog entries should be exceptional, minimal, and traceable in Git history.
- `skills/delivery/` must append a changelog entry for each delivered task (one line: type, task ID, description).
- `skills/release/` consolidates unreleased entries into a versioned release section.

## `AIDEV-NOTE` Comments

- **Goal**: record technical context useful for humans and AIs at critical code points — decisions, constraints, non-obvious tradeoffs.
- **Prefix**: only `AIDEV-NOTE:` is part of the active convention.
- **When to use**: complex logic, fragile integration, non-obvious tradeoff, recurring risk.
- **When to avoid**: obvious comments, code duplication, generic text with no action.
- **Maintenance rule**: keep short and actionable (up to 120 chars), update with code, remove when obsolete.

### Deprecated prefixes (do not introduce in new code)

Earlier versions of this convention included `AIDEV-TODO:` and `AIDEV-QUESTION:`. Empirical audit of derived projects in 2026-06 found near-zero usage:
- **`AIDEV-TODO`** is superseded by task-docs (`memory-system/tasks/`) and GitHub issues for tracked work.
- **`AIDEV-QUESTION`** is superseded by inline human escalation (the agent stops and asks).

Both prefixes remain syntactically legal (existing comments are not invalidated) but **must not be introduced in new code**. Convert existing `AIDEV-TODO` into a task-doc or issue; convert existing `AIDEV-QUESTION` into an explicit escalation when next touched. See ADR-011 in `docs/decisions.md`.

## Code Conventions

### JSDoc tags (required on modified files)

When a PR modifies a JS/TS file under `src/` or a JS file under `public/`, the file must carry minimum JSDoc tags at the top. CI enforces this on-touch (boy-scout rule); existing untouched files are exempt.

**Backend modules (`src/**`)**:
- `@module <name> — <one-line purpose>` at the top of the file.
- `@summary <one-line>` immediately before each public `export`.

**Frontend custom elements (`public/**` that call `customElements.define`)**:
- `@element <tag-name>` and `@summary <one-line>` in the class's JSDoc block.
- Optional but recommended: `@attr <name>`, `@fires <event>`, `@slot <name>`, `@method <name>` for each public surface item.

`docs/INDEX-API.md` is auto-generated from these tags via `skills/gen-api-index`. See `skills/gen-api-index/references/jsdoc-conventions.md` for full examples. Boilerplate `src/` is empty by design, so the convention only takes effect in derived projects.

## Quality Criteria
- Solution addresses root cause.
- Tests pass without hacks.

## Before Implementing

Before creating a new helper, util, component, or module, the agent MUST search for prior art:

1. Consult `docs/INDEX-API.md` if it exists. The generated index lists the public surface of documented modules and frontend custom elements.
2. Run `grep -rn "<related-concept>" src/ public/` (or the project's equivalent source roots) to catch undocumented prior art.
3. Record findings in the task-doc field `prior-art: <file>:<line> — <one-line description>` (one line per finding) or `prior-art: none` if nothing relevant exists.

**Boy-scout rule for undocumented prior art:** if step 2 surfaces a candidate that is not in `docs/INDEX-API.md`, the agent must add the missing JSDoc (`@module` + `@summary` for backend, `@element` + `@summary` for custom elements) to the file it ended up using or referencing. Each task expands the index organically.

`skills/delivery` validates the presence of the `prior-art:` field on task-docs (not the content — epistemic trust stays with the agent; presence signals the search happened).

## GitHub Network / Infrastructure Failures
Transient GitHub infrastructure failures — API/network errors, auth hiccups, rate limits,
and GitHub Actions billing/spending caps — are **NOT** Mandatory Escalation Conditions.
They are frequent; the agent works around them autonomously and does not stop to wait for
the human.
- **Transient `gh`/API/network errors and rate limits:** retry with backoff; use the
  delivery script's REST fallback. Only if a specific operation remains impossible after
  reasonable retries, log it (`gh-unavailable`) and continue with the rest of the work
  where safe — do not block the whole delivery on one flaky call.
- **CI gate blocked by infrastructure** (e.g. `gh-billing-exhausted`: CI output contains
  `recent account payments have failed` or `spending limit needs to be increased`; or the
  required job never starts): the gate is *blocked*, not *failing on content*. Validate
  locally what the gate would check (`./scripts/validate-all.sh`, the governance
  validators, `deliver-to-main.sh`'s local checks, and the CI mode in
  `.governance/ci-mode.conf`). If local validation PASSES, proceed autonomously —
  including `gh pr merge --admin` to bypass the infra-blocked required check. Log the
  literal token (`gh-billing-exhausted`) in the session-log fragment for traceability.
- **Hard line (still binding):** never bypass a check that actually RAN and reported a
  real failure. Bypass only gates blocked by infrastructure, and only after local
  validation of the same substance passes. Never mask a real regression.

## Autonomous Decision-Making

All skills default to autonomous execution. Human escalation is the exception, not the norm. Decisions are resolved using project criteria from `docs/PROJECT_SPECS.md` Section 10.

### Decision Resolution Precedence
1. Explicit human decision (overrides everything).
2. Task file fields and linked task artifacts.
3. `docs/PROJECT_SPECS.md` Section 10 criteria (project-specific first, then defaults).
4. Epic/task documentation and existing code conventions.
5. Conservative assumption that preserves reversibility, documented in the output artifact.

### Mandatory Escalation Conditions
Escalate to human **only** when:
1. Contradictory requirements with no safe resolution using criteria.
2. Security, compliance, or legal risk that criteria cannot safely adjudicate.
3. Irreversible destructive operation with high blast radius.
4. External dependency deadlock requiring product decision.
5. Criteria are genuinely insufficient for the decision at hand.

All other ambiguities must be resolved autonomously using the precedence above.

### Non-Escalable: verification of non-UX behavior
Testing or verifying any behavior that is **not** user-experience (UX) is NEVER a reason
to escalate or hand off to the human. The agent must complete functional verification
autonomously, including end-to-end (e2e) tests of the real wiring (navigation, forms, API
calls, state, error paths). The human's ONLY testing responsibility is **UX** (visual
quality, feel, interaction polish). "I cannot verify this without the human" is not a valid
escalation for functional/wiring/integration behavior — use the available e2e tooling
(`skills/testing/SKILL.md` § Frontend e2e). If e2e tooling is unavailable, the affected
acceptance criterion is marked `FAIL` (blocked on the e2e prerequisite); it is never
delegated to the human and never marked `PASS` without e2e evidence.

### Epic Closing Gate
An epic is **complete only when `ep-check` returns a final `GO`** — i.e. zero-leftover
findings (every finding of any severity resolved, or carrying a human-approved,
recorded, tracked deferral) AND both blocking human gates pass: the architecture-delta
briefing is acknowledged (continuous architectural awareness) and the manual UX test is
`PASS` (or justified `N/A`). The human exercises the UX duty here (`skills/ep-check`
Phase 4.2); agents perform only the e2e wiring check, never the UX verdict.
- Executor skills (`gohorse`, `gohorse-light`, `parallel`) must NOT declare an epic
  complete nor set its `Status: DONE` in `docs/EPICOS.md` on `AWAITING HUMAN VALIDATION`
  or `NO-GO` — only on a final `GO`.
- Finding deferrals are the human's decision alone (an agent never self-approves leaving
  a finding behind), the deferral reason is mandatory and recorded, and Critical/High
  findings are never deferrable.
- The findings→fix→re-check loop uses `ep-check`'s incremental mode so closing an epic
  cleanly does not require repeated full re-validation.

### Decision Documentation
Every autonomous decision must be documented in the output artifact under an "Autonomous Decisions" section:
- `DA-XXX: [decision] — Criteria: [CDC-xxx or default criterion] — Rationale: [brief justification]`

## Escalation
- If scope conflict, dependency conflict, or regression risk appears: pause and record blocker in task file under `memory-system/tasks/`.
